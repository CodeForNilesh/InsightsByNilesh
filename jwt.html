JWT Explained Simply

A JWT is a compact, signed digital identity token used to prove who you are when communicating with a server.

JWT (JSON Web Token) is like a digital identity card. It helps a client prove its identity to a server without the server needing to store session data for every user.

It is compact, signed, and commonly used in modern APIs and authentication systems.

🔑 JWT Basics

Header

Contains metadata such as the token type and signing algorithm.

Payload

Contains claims such as user information, role, and expiration time.

Signature

Ensures the token has not been tampered with.

Example format:

xxxxx.yyyyy.zzzzz

🛠 JWT Flow

  1. Login request: The user sends credentials to the server.
  2. Token creation: The server verifies the credentials and creates a JWT.
  3. Token storage: The client stores it in a browser storage place or cookie.
  4. API request: The client sends the token in the Authorization header.
  5. Token verification: The server checks the signature and claims before granting access.
Authorization: Bearer <jwt-token>

📌 Key Points to Remember

  • Important JWT is not encryption. The payload can be read, but it cannot be changed without breaking the signature.
  • Claims Common claims include exp, iat, and sub.
  • Stateless The server does not need to store session data for each user.
  • Security tip Always verify the signature before trusting the token.

⚠️ Common Mistakes

  • Thinking Base64URL is the same as encryption.
  • Putting sensitive data directly inside the payload.
  • Accepting weak or unexpected algorithms.
  • Giving tokens too long a lifespan.

✅ Advantages

  • Fast because the server does not need to look up session data every time.
  • Portable across different services and APIs.
  • Scalable for modern distributed systems and microservices.

🌐 How Browsers Store JWTs

Browsers do not automatically understand JWTs. They only save tokens when the server or frontend code tells them to do so.

Cookies

If the server sends a Set-Cookie header, the browser stores the token automatically as a cookie.

localStorage

Frontend code can store the token explicitly with JavaScript.

sessionStorage

Similar to localStorage, but it is cleared when the tab closes.

In-memory

The token exists only in JavaScript memory and is lost on reload.

📊 Storage Comparison

Storage Method Auto-saved by Browser? XSS Risk CSRF Risk Persistence
HttpOnly Cookie Yes Low Medium Survives reload
localStorage No High Low Survives reload
sessionStorage No High Low Tab-only
In-memory No Medium Low Lost on reload

⚠️ Risks and Best Practices

  • XSS: Scripts can read tokens stored in localStorage or sessionStorage.
  • CSRF: Cookies are automatically attached by the browser, which can be abused.
  • Best practice: Keep access tokens in memory and refresh tokens in HttpOnly, Secure, SameSite cookies.
  • Modern approach: Consider a Backend-for-Frontend (BFF) pattern for highly sensitive applications.

🔐 JWT Cookies vs localStorage

JWTs stored in localStorage are easy to use but are more exposed to XSS attacks. HttpOnly cookies are safer against XSS, but they introduce CSRF concerns. A hybrid design is often the best approach.

Option XSS Risk CSRF Risk Best Use Case
localStorage High Low SPAs using manual Authorization headers
HttpOnly Cookies Low Medium Safer refresh/session token storage
BFF Pattern Lowest Low Highly sensitive apps

🔄 Refresh Tokens

Refresh tokens are long-lived credentials used to obtain new short-lived access tokens without asking users to log in again.

Access token

Short-lived and sent with most API requests.

Refresh token

Longer-lived and used only to obtain a new access token.

  1. Login creates both tokens.
  2. The client uses the access token until it expires.
  3. When it expires, the client refreshes it using the refresh token.
  4. The server can rotate and revoke refresh tokens for better security.

✅ Recommendations for a .NET Developer

  • Use HttpOnly, Secure, and SameSite cookies for refresh tokens.
  • Keep access tokens in memory and refresh them silently when needed.
  • Avoid storing sensitive JWTs in localStorage or sessionStorage.
  • Consider the BFF pattern if your application deals with finance, healthcare, or other sensitive data.
